Proposal for Cris · 28 September 2026

Logging that lets us recreate any video

Cris asked for a complete log system: every prompt, reference image, input and setting, so that when something goes wrong we can recreate it. This document explains the problem, every approach we researched, how each would work for Diamond Studio, what it would cost, and a step-by-step plan. It is research and planning only. No code has been changed.

Prepared by Sahil Koshriya About 20 minutes to read Status: waiting for Cris's decision Covers desktop app · auth-service · website

1 · Summary

  • The request is three jobs. (1) Save each video's full recipe: settings, prompts, reference image, script, and what the AI sent back. (2) Keep a diary of what the server did on every AI call. (3) Catch failures on the customer's PC: narration, video assembly, Whisper and crashes. Today we never see any of the third. No single tool is good at all three.
  • Papertrail would work for job 2 only. On small plans you can search only the last week or two, it stops accepting logs once the monthly allowance is used up, and SolarWinds forced its customers to migrate in 2025.
  • Recommendation: setup B, Azure + Sentry. Server logs go to Azure Log Analytics, which already collects them, with the first 5 GB a month free. Recipes go to our own database and file storage. Sentry catches crashes on customers' PCs. Customer content stays in our Azure account.
  • Cost doesn't decide this. By our estimate, 1,000 long videos a month is about 0.3 GB of text. That fits almost every free plan. What decides it is where customer content is kept, whether we can see PC failures, and how easy the logs are to search.
  • Next step: Cris answers four questions (section 13). Then six tickets, and the first one is small.

2 · The problem

What Cris asked for, and why it matters

The request, in short

A complete log system, on Papertrail or a similar platform, that shows everything that happens: which prompt a customer used, which reference image, the inputs and the exact settings, so that bugs can be recreated.

A support case today

This is what happens now when a customer writes in. Nothing here is invented: each step follows from how the app and server work today.

  1. 1A customer writes: "The app stopped at the audio step."
  2. 2We check the server. Nothing is there: narration runs on their PC through Microsoft's Edge TTS and never touches our server.
  3. 3We ask for their log file. It's in a hidden system folder that most customers can't find.
  4. 4We ask which settings they used: voice, language, style, length. They don't remember.
  5. 5We try a different topic with our own settings. It works for us, and the case is closed as "can't reproduce".

The request is really three jobs

"Log everything" mixes three needs. They differ in size, in shape and in where they happen, and a tool that is great at one is usually poor at another.

JOB 1

A recipe for each video

"What exactly went into video X?"

Holds
Topic, all settings, every prompt, the reference image, the script, and what the AI sent back.
Shape

Best home

JOB 2

A diary of the server

"Which call failed, for whom, and when?"

Holds
Every AI call: user, video, step, model, time taken, error.
Shape

Best home

JOB 3

Failures on the customer's PC

"What broke on their machine?"

Holds
Narration (Edge TTS), video assembly (FFmpeg), Whisper, crashes, startup failures.

Best home

Where each step runs, and what we can see today

The app runs 13 steps. Eight involve our server (fact-check and revise share one call), six run on the customer's PC, and steps 6 and 12 do both. "Visible" here means something we could look at without asking the customer.

3 · Starting point

What we already have, and what's missing

Half of the plumbing already exists. Each item below was checked in the code.

Already in place

  • A log file on each PC: 2 MB with 3 backups. It stays on the customer's machine.
  • A video ID. generation_id is a UUID created when a run starts, before research, and saved in generation_id.txt so a resumed run keeps it.
  • One exit door for AI calls. All nine desktop AI calls send their headers from one function in the desktop code.
  • The server sees every AI input and output: research, fact-check, script, voice-over, scenes, images, SEO, chapters.
  • Azure already stores what the server prints. Our hosting environment came with a Log Analytics workspace.
  • A few useful server lines: word counts, provider errors, and the first 400 characters of an unusable AI reply.
  • A per-video record for billing: a table keyed by user and video ID.
  • Patterns to copy: the reference-image purge job (#136), scheduled jobs, the rate limiter, the emergency-stop runbook.

Missing

  • The video ID travels only with image calls. The other eight calls can't be tied to a video.
  • Server logs are plain text and mostly errors. There's no line per call saying user, video, step and time taken.
  • No record of the settings a run used.
  • Nothing from the PC reaches us: narration, FFmpeg, Whisper, crashes and startup failures.
  • AI outputs aren't kept anywhere we can reach. They exist only as files on the customer's PC.
  • No time limit or delete rule for any of this.
  • No privacy-policy wording for this kind of data yet.
  • No test that stops a secret from ever being logged.

Azure Log Analytics

Azure's own log store. It's already switched on for our server, and it already receives everything the server prints.

Cost · 1,000 videos$0 a month
Cost · 10,000 videos$0 a month
Kept for31 days included

What it is

When our hosting environment was created, Azure attached a Log Analytics workspace to it. Everything the server writes to its console lands in a table called ContainerAppConsoleLogs_CL. We search it with Azure's query language, KQL. The first 5 GB a month (per billing account) is free, and after that it costs $2.30 per GB. Azure's request tracing, Application Insights, can later be added on the same workspace through OpenTelemetry.

Example

Cris pastes a video ID into this saved search and sees that video's whole server history in order:

ContainerAppConsoleLogs_CL
| where ContainerAppName_s == "our-api"
| where Log_s has "7f3c9a1e-2b4d-4e8f-9a61-5c0d2e7b91ae"
| project TimeGenerated, Log_s
| order by TimeGenerated asc
14:02:11 ai.call step=research   outcome=ok    ms=41200
14:03:02 ai.call step=script     outcome=ok    ms=96100 model_calls=3
14:04:40 ai.call step=voiceover  outcome=error kind=busy attempt=3/3

We already have

  • The workspace, collecting automatically
  • 5 GB a month free, 31 days kept
  • Access through the Azure Portal

We would need

  • The server to print one JSON line per AI call, with the video ID (the foundation ticket)
  • A few saved searches and one alert for error spikes
  • Optionally a daily cap as a safety net. It stops collecting when hit, so treat it as a guard, not a budget.

Approach 2 · job 1use it

Our own recipe store

Not a log tool but a database table: one row and one file per video, holding everything needed to recreate it.

Cost · 1,000 videos≈ $0.02 a month
Cost · 10,000 videos≈ $0.15 a month
Kept forWe decide

What it is

A new Postgres table keyed on the generation_id the app already creates. The row holds the small things: user, app version, settings, each step's result, and when it expires. The big things (research, script, voice-over text, scene descriptions, image prompts and, if Cris agrees, a copy of the reference image) go in one Azure Blob Storage file per video, and the row points to it. The server writes most of it, because the AI inputs and outputs already pass through it. The desktop adds only what the server can't see.

Example: the recipe for one video

  "settings": { "CONTENT_STYLE": "Podcast", "PODCAST_STYLE": "Casual Conversational",

We already have

  • Postgres and migrations (Alembic)
  • A per-video billing row to link to
  • A purge-job pattern to copy (#136)
  • A managed identity for the server

We would need

  • A private storage account + container
  • The table + migration, tested up, down and reseeded
  • AI routes adding each call's input and output to the file
  • A clean-up job, and a Blob lifecycle rule as a backup
  • Delete a customer's recipes when their account is deleted
  • A way to read them: SQL first, an admin page later

Approach 3 · job 3 (+2)use it

Sentry

The standard tool for "the app broke on a customer's machine". It runs inside the desktop app and reports crashes to us.

Cost · 1,000 videos$0 (1 user) · $26 (team)
Cost · 10,000 videos$26 a month
Kept for30 days free · 90 on Team

What it is

Sentry's Python library sits inside the desktop app. When something fails, it sends the error, the exact line, the steps just before it, the app version and any tags we add, such as the video ID. Identical crashes are grouped into one issue with a count of affected users, and an email alert goes out. It also works on the server and now takes logs too (5 GB included). The free plan has one user. Team costs $26 a month on yearly billing, with unlimited users and 50,000 errors.

Example: a real, open bug

Edge TTS sometimes fails with NoAudioReceived. It's an open issue upstream (edge-tts #473). Our retry makes three attempts and then stops the run. Today we can't tell how many customers hit it. With Sentry we would see one issue, something like "NoAudioReceived in generate_tts · 23 users · app 3.2.0 · voice es-MX-JorgeNeural", tagged with each video ID. That tells us whether to bump the library, change the retry, or ignore it.

We already have

  • One place to start it, before the licence check
  • An app version number
  • A video ID to tag reports with

We would need

  • An account and two projects (desktop, server), US or EU storage
  • A cleaner that strips secrets before sending. Sentry does not clean attached files, so we clean them first.
  • A check that the installer includes it and the app starts offline
  • A way to change its key without a new release. Its key is safe to be public (send-only) but can be abused, so our server could hand it out at login.

Papertrail

A hosted log viewer: a live stream of lines with a search box, like a terminal in the browser. Owned by SolarWinds.

Cost · 1,000 videos≈ $7 a month
Cost · 10,000 videos≈ $40 a month
Search window≈ 1–2 weeks

What it is

Papertrail receives logs over syslog, a standard protocol Python supports out of the box, and shows them live. Small plans keep logs searchable for about 1–2 weeks and archive older ones as files for a year. When the month's allowance runs out, it stops accepting logs until you upgrade. In 2025 SolarWinds moved Papertrail accounts onto "SolarWinds Observability". One forum thread mentions a 4 September 2025 deadline, and a long-time paying customer wrote publicly that their account was suspended during the move. The prices here come from a pricing tracker; the official page says "from $5 per GB".

Example

Cris opens Papertrail, types 7f3c9a1e, and watches that video's server lines scroll past live. Three weeks later the customer writes in about the same video, and those lines are no longer searchable.

We already have

  • Python's built-in syslog handler
  • Container App secrets to hold the send address

We would need

  • An account and a plan
  • A handler behind a queue, so a slow Papertrail never slows a request
  • The desktop to go through our server (a key in the app would leak)
  • The recipe store anyway, because Papertrail can't hold scripts and images

AI-call recorders (LLM observability)

Tools built to record every prompt and every AI reply as a timeline, which is exactly the "which prompt did the user use" part of Cris's message.

Cost · 1,000 videos≈ $32 a month (Langfuse)
Cost · 10,000 videos≈ $130 a month
Kept for30–90 days

What they are

Langfuse, LangSmith, Helicone, Arize Phoenix and Pydantic Logfire record each AI call's prompt, reply, token count and time, grouped into sessions, so a video would be one session. OpenTelemetry has a standard for this, the GenAI conventions, which makes recording prompt text opt-in by design. That's a good safety property. They charge per call, though, and one long video makes about 135 calls, which is why they cost the most here.

Approach 8 · jobs 1 + 3use it

Desktop run report

The app sends a small, cleaned report to our own server, either automatically or when the customer presses "Send report".

Cost · 1,000 videos$0
Cost · 10,000 videos$0
Kept forWith the recipe

What it is

At the start of a run, the app sends its settings (picked from an allow-list, never "everything minus secrets"), the app version and the Windows version. At the end, or when a step fails, it sends each step's result, the error, and the last lines of the local log with secrets removed. It's sent in the background with a short timeout, and it can never stop or slow a run. That's the same rule the local log already follows: losing the log must never stop the app. The opt-in variant sends only when the customer presses a "Send report" button.

Example

run report · 7f3c9a1e… · app 3.2.0 · Windows 11
research ok · fact-check ok · script ok · audio FAILED (NoAudioReceived after 3 tries)
voice es-MX-JorgeNeural · rate +0% · pitch +0Hz · language Spanish

We already have

  • The local log file and its "never stop the app" rule
  • An authenticated client
  • The server's rate limiter
  • Five language catalogs for any button text (#193)

We would need

  • A server endpoint with a size cap and a rate limit
  • The settings allow-list
  • A background sender
  • Automatic vs. button: Cris decides

9 · Worked examples

Four bugs, today and with setup B

Narration fails on a customer's PC

Based on a real, open upstream issue: Edge TTS "No audio was received" (edge-tts #473).

Today

  • The server sees nothing
  • We ask for a hidden log file
  • We can't tell if it's one customer or hundreds

With B

  • A Sentry issue counts every customer hit, by app version and voice
  • The run report marks audio as failed
  • The recipe shows the voice, rate and language
  • We decide with numbers: bump the library, change the retry, or wait

The voice-over step stops with "server busy"

Today

  • The server logs a warning with no user or video
  • The customer sees a Spanish error
  • We can't tell a provider outage from bad input

With B

  • A KQL search by video ID shows 3 attempts, kind=busy, and the times
  • A second search shows whether other users failed in the same minutes (provider outage) or only this one (input problem)
  • The recipe shows the script length that went in

"The images don't match my topic"

A quality bug, not a crash, and exactly Cris's "which prompt did the user use".

Today

  • We can't see the prompts
  • We'd need their topic, content style, animation style and interval, and they won't know them all

With B

  • The recipe holds CONTENT_STYLE, ANIMATION_STYLE, every scene description and every image prompt
  • We can see whether the scene step or the style text caused it
  • We re-run with the same recipe to confirm the fix

The app closes at start-up

Today

  • Nothing reaches us: the failure happens before login, so the server never sees this customer
  • Only the local log file knows (#168)

With B

  • Sentry starts before the licence check, so the crash is reported with the app and Windows version
  • A packaging mistake shows up after the first few installs, not after the first angry email

10 · Implementation plan · no code yet

How setup B would be built

The work splits into a foundation that every option needs and four building blocks. Sizes are relative (S small, M medium, L large), not days. The other setups reuse the same blocks. The setups table shows which.

Foundation

S–M · every setup
  1. The desktop sends the video ID on every AI call. All nine calls (research, fact-check, script, voice-over, scene, image, reference upload, SEO, chapters) send their headers from one function, so this is one change in one place. daimond-app
  2. The server reads the ID and the user on every request and attaches them to every log line. This goes next to the existing API-key check. auth-service
  3. One JSON line per AI call: step, provider, time taken, outcome and error kind, from the AI routes. If a planned clean-up that gives them one shared helper lands first, this goes there instead. auth-service
  4. A short excerpt of what the AI returned when a step fails, the way the server already does for unusable replies. auth-service
  5. A secret-leak test that fails if the API key, a login token or a license key ever appears in a log line. auth-service

This alone turns Log Analytics into a usable server diary. Nothing else is needed for job 2.

Recipe store

M–L · job 1
  1. A private storage account and container. The server's managed identity gets write access, recorded in the deployment runbook. Azure
  2. The recipe table and its Alembic migration, tested up, down and reseeded. auth-service
  3. Each AI route adds its input and output to the video's file as it goes. auth-service
  4. A clean-up job like the reference purge: file first, then row, for the same reason #136 gives. A Blob lifecycle rule acts as a backup. auth-service · Azure
  5. A customer's recipes are deleted when their account is deleted. auth-service
  6. Reading them: SQL plus a Portal download first; an admin page later if needed. app-frontend, later

Run report

M · jobs 1 + 3
  1. An endpoint behind the same login and API key, with a size cap and the existing rate limiter. auth-service
  2. At run start: settings from an allow-list, plus the app and Windows version. daimond-app
  3. At the end or on failure: step results, the error, and the last log lines with secrets removed. daimond-app
  4. Sent in the background with a short timeout. It can never stop or slow a run. daimond-app
  5. If opt-in: a checkbox or button in Configuración › Sistema, with its text in all five language catalogs. daimond-app

Sentry

S · job 3
  1. An account with a desktop project and a server project, US or EU storage, and email alerts. Sentry
  2. Start it before the startup gate. Label reports with the app version and tag each run with its video ID. Clean every report before sending, and attach the cleaned settings. daimond-app
  3. Check that the installer build includes it and that the app starts with no internet and no Sentry key. daimond-app
  4. Optional: the FastAPI integration on the server, with personal-data sending off. auth-service

How every ticket is verified

  1. The full test suite passes in every repo the ticket touches, before anything is pushed.

11 · Guardrails

Rules that apply to every option

  1. One ID per video on every call. Without it, nothing joins up.
  2. Never write secrets: API key, login tokens, license keys, payment details. The OWASP logging guide says the same about session tokens and passwords.
  3. No images inside log lines. Store the file and log its ID.
  4. No log-tool keys inside the desktop app. Sentry's send-only key is the one exception.
  5. Log through Python's standard logging, in JSON. Switching tools becomes a settings change.
  6. Record what the AI returned, not only what we sent. The same inputs give different outputs every time.
  7. Every piece of data has an expiry date and can be deleted per customer.
  8. The customer's own log panel doesn't change. The #102 rule stands: customers are never shown image counts.

12 · Privacy

Customer content is personal data

Topics, scripts and reference images belong to the customer, and a reference image may show a real person's face. Colombia's Ley 1581 of 2012 (with Decreto 1377 of 2013) governs personal data. The SIC's Circular Externa 005 of 2017 lists the United States among countries with adequate protection, so US-hosted tools like Sentry are allowed destinations. We still owe customers a clear policy, and ticket T3 makes sure it covers this data.

What the policy should say:

  • What we collect: settings, topics, AI outputs, errors, app and Windows version
  • Why: to fix problems and recreate failed videos
  • Where: our Azure account and Sentry (US or EU)
  • How long: the retention Cris picks (for example 30 or 90 days)
  • Who can see it: the two of us
  • How to ask for a copy or for deletion

This is research, not legal advice. Whoever handles legal should confirm the wording.

14 · Glossary

Words used in this document

Log / log line
One written record of something that happened, with a time.
JSON line
A log line written as named fields (step=script) instead of free text, so tools can filter by any field.
Video ID
generation_id: the UUID the app gives each video, reused when a run resumes.
Recipe
Everything needed to recreate a video: settings, inputs, prompts and outputs.
Log Analytics
Azure's log store. Ours already receives the server's console output.
KQL
Kusto Query Language, used to search Log Analytics.
Blob storage
Azure's file storage for large files, priced per GB per month.
Retention
How long data is kept before it's deleted.
Ingestion
Sending data into a log tool. Most tools charge for it per GB.
Crash reporter
A library inside an app that sends errors to a service like Sentry.
DSN
Sentry's project key. It can only send data, never read it.
Syslog
An old, standard way of sending log lines over the network. Papertrail uses it.
OpenTelemetry
An open standard for logs, traces and metrics, so the tool behind it can be swapped.
Trace / span
A timeline of one request (trace) made of timed steps (spans).
LLM observability
Tools that record AI prompts and replies, such as Langfuse.
Allow-list
A list of what may be sent. Anything not on it is left out, which is safer than a list of what to block.
Managed identity
An Azure login for our server itself, so no password is stored.
Lifecycle rule
A Blob setting that deletes files automatically after N days.
